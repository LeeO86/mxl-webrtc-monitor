## 2. Deviations

1. **v210 unpack is GStreamer's CPU `v210` raw format** (`video/x-raw,format=v210` into `videoconvert`). There is no separate GPU unpack. `video/v210a` is accepted: the fill plane is pushed as v210 and the alpha plane is ignored.
2. **Default NMOS seed is `HOST_ID-monitor`**, matching the configuration table. The prose also mentions the container name; under host networking `HOST_ID` is the host or pod name. Set `NMOS_SEED` to override it.
3. **IDs are UUIDv5** in the RFC 4122 URL namespace. The name is `mxl-webrtc-monitor/<seed>/node` (and `/device`, `/ch/<n>/video`, `/ch/<n>/audio`).
4. **Audio meters are computed in the reader** (peak and RMS, about 10 Hz), not by the GStreamer `level` element. `METRICS_AUDIO_PEAK` defaults to false and is not in the spec table.
5. **Opus is the only audio codec.** MediaMTX 1.20.1 documents Opus as an HLS codec, so no AAC track is added.
6. **The Query API defaults to `NMOS_REGISTRY_ADDRESS` and `NMOS_REGISTRY_PORT + 1`.** Set `NMOS_QUERY_ADDRESS` and `NMOS_QUERY_PORT` when the Query API is elsewhere. Sender labels and `/readyz` use that API. There is no output domain: `MXL_OUTPUT_DOMAIN_DIR`, `MXL_OUTPUT_DOMAIN_ID` and `history_duration` do not apply, and `MXL_CLEANUP_ON_EXIT=true` does not delete anything. SIGTERM exits 143 after readers are released and the node is removed from the registry.
7. **A missing MXL root does not exit 78.** Exit 78 is invalid configuration. Readiness stays false until the directory exists, NMOS is registered or disabled, and the MediaMTX API answers.
8. **Unrouted audio omits the audio track.** Routed audio that has not produced samples yet pushes digital silence so the player keeps a continuous timeline.
9. **DNS-SD off** sets nmos-cpp `pri` and `highest_pri` to `no_priority`, which disables advertisement and discovery. `NMOS_DNS_SD=true` leaves the nmos-cpp defaults.
10. **Per-channel settings** are `CH<n>_*` environment keys and a `channels` array in the JSON file. They apply at runtime. Global keys changed through the UI set `restart_required`.
11. **x264 uses `ultrafast` and `tune=zerolatency`**, GOP of about one second, no B-frames. NVENC is `nvcudah264enc` with CBR, preset `p1`, tune `ultra-low-latency` and zero reorder delay, fed NV12. The spec names `nvh264enc`; its legacy presets fail on current drivers (deviation 13).
12. **The demo Compose registry is the Python stand-in** in `tests/integration/fake_registry.py`. It implements the registration and query calls this process makes. A facility deployment sets `NMOS_REGISTRY_ADDRESS` to a real registry.
13. **NVENC element is `nvcudah264enc`, not `nvh264enc` (spec §5.5).** With driver 595.84 `nvh264enc preset=low-latency-hq` fails at caps time with "Selected preset not supported", and `nvh264enc` cannot take the P1-P7 presets. `nvcudah264enc` (GStreamer 1.24, same plugin) can. An encoder error after PLAYING also falls back to x264 for that channel, as §5.5 asks for session failures.
14. **Audio follows the pushed video (1.0.5).** Audio timestamps count pushed samples. 1.0.4 pushed one video frame of audio each time the audio head moved; a fabrics mirror moves it 480 samples every 10 ms, so the audio ran at twice real time, `rtspclientsink` held the audio branch and MediaMTX got an Opus track without samples (platform test-all-mon, lab repro). Now the audio pushed equals the samples the pushed video frames cover, read from a cursor after the last pushed sample; a cursor more than three frames from the alignment target is placed again (`resyncs_total`), a gap becomes silence. Late audio (mirror) is read at its head, unaligned.

15. **Web UI 1.1.0** follows mxl-test-player 1.1.0, mxl-replay 1.3 and mxl-multiviewer 1.2 (same `style.css` tokens and rules, `Pill`, `Segmented`, tabs with `#hash`, theme from `prefers-color-scheme`). It stays one embedded HTML file (`vite-plugin-singlefile`). The multiview tab stays mounted, so other tabs do not stop its players. Each tile owns its player (`web/src/player.js`, the 1.0.5 logic) and starts it again only when `playbackKey` changes; a WebRTC session that played and then drops starts again after 1.5 s (a settings change rebuilds the channel's stream, and 1.0.5 then switched to HLS for good). Channel drafts and settings edits live in `web/src/store.js`. The Status tab reads its counters from `/metrics` instead of a new API. Settings are saved with `PUT /api/v1/config`, which replaces the file layer, so the page sends every `file` key plus the edits; channel keys are edited on the Channels tab (`PATCH`).
16. **MediaMTX path state (1.1.0).** The viewer poll (`GET /v3/paths/list`, once a second) also keeps `ready` and `tracks` per `ch<n>` path, parsed by `mediamtxPathsFromList`. A channel without a path is reset to not ready and 0 viewers. The HTTP client joins chunked bodies: MediaMTX sends that list chunked above 2 KiB, and before 1.1.0 the viewers stayed 0 with two or more paths.
17. **MediaMTX RTSP is TCP only (1.1.0).** The generated `mediamtx.yml` sets `rtspTransports: [tcp]`, as the channels publish with `protocols=tcp`. Otherwise every MediaMTX binds UDP 8000 and 8001, and a second monitor on the host cannot start its sidecar.
18. **IS-04 receiver labels stay `Monitor <n> Video` / `Monitor <n> Audio`.** `CH<n>_VIDEO_LABEL` and `CH<n>_AUDIO_LABEL` name the channel in the UI, `/api/v1/channels`, `/api/v1/nmos` and the overlay; the registered receivers keep the default labels (spec §4.1 says configurable; open).
19. **TSL tally (1.2.0, platform request T3)** is mxl-multiviewer 1.3.0's receiver (`src/control/tsl.cpp`, its spec §7) ported to `src/tally/tsl.cpp`: the same parser, UTF-16 conversion, colour rule (`effectiveTally`), index map and API field names. A listener thread polls the UDP socket, the TCP listen socket and up to 8 clients, and writes the fields into the `ChannelBook`. Differences:
    - `TSL_ENABLE` defaults to **false** (multiviewer: true). With true, a second monitor on a host (host networking) would exit 75 on the TSL ports after an update to 1.2.0, a break of the 1.x contract.
    - Default ports **8912/udp and 8913/tcp** (multiviewer: 8910/8911). Both repos run with host networking, so a monitor and a multiviewer on one host would collide on 8910/8911.
    - TCP: DLE/ETX is optional. A packet also ends at `PBC` + 2 bytes or at the next DLE/STX, as the platform's reference codec (`tsl5.py`) frames it. The multiviewer waits for DLE/ETX.
    - ASCII text: a byte above 0x7F becomes U+FFFD, as the reference codec decodes it, so `tsl_text` stays valid UTF-8 (the multiviewer passes the byte through).
    - No TSL 3.1 (`TSL_V31`) and no `tsl_messages_total` metric: not asked for.
    - `TSL_SCREEN` and `TSL_MAP` apply after a restart like every global key here (multiviewer: at runtime).
    - The tally is drawn by the page (lamps, picture border, label background with `tally_text`), not burned into the H.264 preview. `tally_text` is a channel setting (`CH<n>_TALLY_TEXT`), the analogue of the multiviewer's per-tile option.
20. **Preview contract (1.3.0, platform §11.5 / D-185)**, spec §5.7:
    - **MediaMTX built in, not a sidecar.** Feasible: MediaMTX is MIT (redistribution with its notice, which the image keeps in `/usr/share/doc/mediamtx/LICENSE`) and one static Go binary of about 55 MB (image 739 → 794 MB). The Dockerfile copies it from the pinned official image (`MEDIAMTX_VERSION`, 1.20.1). `src/ops/child.cpp` runs it: fork and exec of `mediamtx <MEDIAMTX_CONFIG_PATH>` from `PATH`, `PR_SET_PDEATHSIG` SIGTERM, its own process group (a terminal's Ctrl-C reaches only the monitor), file descriptors above 2 closed; restart after an exit after 1 s, doubling to 10 s, 1 s again after 10 s of running; stop with SIGTERM and SIGKILL after 3 s. The child is waited for without reaping (`waitid` with `WNOWAIT`) so a stop never signals a reused pid. The sidecar mode was not needed as a fallback.
    - **Mode.** Own when `PREVIEW_PUBLISH_URL` is empty, shared when set. The RTSP ingest of the own MediaMTX moved from `MEDIAMTX_RTSP_URL` (now an alias of the publish URL) to the new `MEDIAMTX_RTSP_PORT`, so two monitors in own mode on one host can still separate it.
    - **Aliases.** `MEDIAMTX_RTSP_URL`, `MONITOR_WHEP_PUBLIC_URL` and `MONITOR_HLS_PUBLIC_URL` are renamed in each layer (environment, file) before the layers merge, so the environment's old name still beats the file's new one; within a layer a set new name wins. The API, the page and the export show only the new names. Read literally, the alias makes a 1.2.0 sidecar deployment (the platform chart sets `MEDIAMTX_RTSP_URL`) a shared-mode one; because the config file is still written in both modes, its sidecar keeps working (lab check below). A sidecar deployment without `MEDIAMTX_RTSP_URL` (this repo's 1.2.0 Kubernetes example) runs the built-in MediaMTX and its sidecar fails to bind: the CHANGELOG says to drop the sidecar.
    - **Path prefix.** `PREVIEW_PATH_PREFIX` defaults to `mxl-webrtc-monitor` (the function's own name), so 1.3.0 URLs are `/<prefix>/ch<n>/...` also standalone; the page follows the API. An empty value is the default (no way back to bare `ch<n>`).
    - **Shared mode and the API.** `MEDIAMTX_API_URL` defaults to empty there: the platform's MediaMTX is not reachable on localhost. When set, viewers and path state come from it. `/readyz` needs MediaMTX only in own mode; a shared MediaMTX that is down shows as publish errors, not as an unready pod.
    - **Publish state** is measured at the RTSP sink, the same in both modes: a pad probe counts buffers leaving the queue in front of `rtspclientsink`. That sink holds the first buffer until MediaMTX took ANNOUNCE, SETUP and RECORD (rtspclientsink 1.24 posts no completion message for RECORD), so more than two buffers mean the stream is published. A bus error sets `error` with its message until the next stream publishes. `PREVIEW_PUBLISH_URL` must not carry credentials (it would leak into the export); a shared MediaMTX has to accept publishing without them.
    - The playback URLs use the path each channel publishes since the start, so a changed prefix (restart required) does not point the page at a stream that does not exist yet.
21. **Widgets (1.3.0)**, spec §6.6: `/widget/channel` serves the same embedded page as `/`; `main.js` mounts `WidgetPage.vue` instead of the app for `/widget/*`, which shows one `ChannelTile` in its new `widget` mode (no panel border, no status lines or mute; title with `labels`, meters with `meters`). The server checks the query (400 for a bad `ch`, `labels`, `meters` or `theme`) and adds the CSP header only on these routes; nothing else of the app changes. `theme` sets `data-theme` on `<html>`: light and dark force the colour tokens, transparent keeps the dark ones on a transparent background and removes the page's `color-scheme` meta, because a frame whose colour scheme differs from its parent's is painted opaque. The widget uses the store's live connection (WebSocket and polls) like the app. `/widgets` has no CORS headers (the platform reads it server side).

## 3. Process

One nmos-cpp node exposes a video receiver and an audio receiver per channel. Each channel has a video reader thread and an audio reader thread. They resolve the domain on every attempt (no negative cache), open the MXL reader, and push into a leaky `appsrc`. A slow encoder drops the oldest buffer and increments `grains_dropped_total{reason="queue_full"}`. Falling out of the ring resynchronises to head minus `READ_OFFSET_GRAINS` and increments `resyncs_total`.

The video thread publishes an H.264 elementary stream. The audio thread publishes Opus when that receiver is enabled. Both go to the channel's RTSP path (below) over TCP. MediaMTX serves WHEP and low-latency HLS.

With `TSL_ENABLE=true`, one more thread receives TSL 5.0 on UDP and TCP and sets each addressed channel's tally in the `ChannelBook`; the API and the WebSocket carry it from there.

The streams go to `<publish URL>/<PREVIEW_PATH_PREFIX>/ch<n>`: in own mode the process's MediaMTX child on `127.0.0.1:MEDIAMTX_RTSP_PORT`, in shared mode `PREVIEW_PUBLISH_URL`.

- Unit tests cover config precedence, IS-05 UUID validation, UUIDv5 ids, the channel state machine, domain scan including mirror domains, audio pair selection, backoff, public WHEP/HLS URL parsing, announce-address checks, query-port defaults, tags, config export/import, IS-05 state reload, the MediaMTX path list, the channel status fields of 1.1.0 and the info label, and that a rejected `PATCH` or `PUT` leaves the settings as they were. `tests/unit/test_tally.cpp` (1.2.0) checks the TSL parser against byte vectors of the platform's reference codec (`tsl5.py`, platform commit a1883cb: UTF-16 and ASCII, several displays, DLE stuffing, with and without DLE/ETX, reads split at every byte), control data, screen control, a lone surrogate, short packets, the display map and screen filter, the colour rule, the `TSL_*` settings, and the tally fields and `tally_text` in the API.
- `tests/integration/monitor.sh` writes a v210 and float32 flow, PATCHes channel 1, waits for `running` (video and audio), checks that the HLS playlist grows segments and that the channel reports its MediaMTX path ready with an H.264 track, stops the writer and expects `no_signal` (video and audio), activates a missing flow and expects `waiting`, then creates that flow and expects `running` without another PATCH. In between it sends a TSL 5.0 packet over UDP (UTF-16 label) and one over TCP (DLE/STX with a stuffed 0xFE) and checks the tally fields of channel 1. It sets `MONITOR_HLS_PUBLIC_URL` and fetches the playlist through the URL the API reports. ## 5. Public WHEP and HLS URLs

`PREVIEW_WHEP_URL` and `PREVIEW_HLS_URL` (1.2.0: `MONITOR_WHEP_PUBLIC_URL` and
`MONITOR_HLS_PUBLIC_URL`, still accepted) are optional absolute
origins. When set, `/api/v1/channels` returns
`<origin>/<prefix>/ch<n>/whep` and `<origin>/<prefix>/ch<n>/index.m3u8` and
`playback.public.whep` / `playback.public.hls` is true. The page does not
rewrite a public URL. When a setting is empty, that URL stays
`http://<MONITOR_PUBLIC_IP>:<port>/<prefix>/ch<n>/...` and the page still replaces only
the hostname. An `https:` page shows a banner when a playback URL is still
`http:`, and a hint on a tile that can play neither. ICE and `webrtcAdditionalHosts` stay on `MONITOR_PUBLIC_IP`.

A same-origin proxy of WHEP and HLS through the monitor's own web server is
not implemented.
